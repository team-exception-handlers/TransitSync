# SOEN 490 code workflow (TransitSync)

TransitSync is graded with the SOEN 490 Code Quality Rubric (38% of the grade) plus graduate attributes. The same rules apply in Releases 1 to 3; the bar rises each release. This skill turns the rubric into concrete steps. Project rules in `CLAUDE.md` and the `transitsync-*` skills still apply; if a general rule conflicts with them, follow `CLAUDE.md`.

GitHub access is read-only. Claude writes code and drafts text (commit messages, PR descriptions, issue comments). The team commits, pushes, opens PRs and posts.

## Before starting a task

1. Read the task issue and its parent user story (`gh issue view <n>`). Do not start a story that is missing its full statement, points, priority, risk, feature label or milestone; say what is missing instead
2. Check dependencies named in the issue. If something it needs is not merged, build against the agreed interface with a fake or fixture and say so
3. State the plan in a few lines: files to add or change, tests to write, which rubric checks are touched

### Structure (section 3)
- Files below 500 lines where possible; functions at or under 50 lines; cyclomatic complexity at or under 15. Ruff enforces complexity and statement count in CI. Split before the limit, not after. If a file must stay over 500 lines, add a comment at the top giving the technical reason
- Comments and docstrings make up 20 to 30% of each source file's lines, where applicable (see "Comments" below)
- One responsibility per class or module. No circular imports. Simulator core must not import API or web code
- No duplicated block of 20+ lines in 3+ places. Formulas, caps and thresholds have one source of truth (config or one module)
- No `TODO`/`FIXME` for required behaviour, no `NotImplementedError` or placeholder returns, no commented-out code, no unused files, functions or duplicate alternative implementations
- PEP 8 naming: `snake_case` functions/variables/modules, `PascalCase` classes, `UPPER_CASE` constants. TypeScript: `camelCase` variables/functions, `PascalCase` components/types. Use Mathematical Foundations symbols where they exist
- If code must break one of these rules, add a comment next to it giving a specific technical reason and why it beats the alternatives. "Necessary" or "generated by AI" is not a reason

### Comments (team rule, Iteration 3 on)
Target: comments and docstrings are 20 to 30% of the non-blank lines in each new or changed source file (Python, TypeScript, SQL). "Where applicable" means very small files (constants, `__init__.py`, type-only files) can be lower; do not pad them.
- Every module starts with a docstring (Python) or header comment (TypeScript) saying what the file is for and where it fits (simulator, API, front end)
- Every public class and function has a docstring: what it does, its inputs and units (seconds, passengers), what it returns, and the errors it raises
- Inside functions, comment each logical step that is not obvious: why a rule exists, which Mathematical Foundations section a formula comes from, why an edge case is handled that way
- Do not restate the code (`# increment i`), and never leave commented-out code
- Measure with `cloc --by-file --quiet <files>`: ratio = comment / (comment + code). cloc counts Python docstrings as comments. Report the ratio for each new or changed file in the finishing block
- This rule overrides any general advice to match the surrounding comment density. Do not edit untouched files only to raise their ratio

### Validation, errors, logging (section 4)
- Validate every user or external input for type, format, range and required fields before using it (Pydantic models in the API, explicit checks in scripts). Return a clear error naming the bad field
- Handle file, database and network failures explicitly. No bare `except:`, no `except Exception: pass`, no swallowed errors
- Never show stack traces or internal details to users; log them instead
- Use `logging` with `log = logging.getLogger(__name__)`, never `print` (except plain CLI output). Levels: `debug` detail, `info` normal milestones, `warning` recoverable problems, `error` failures. Include useful context (feed_id, scenario id, seed, issue being processed)
- Never log secrets, connection strings, tokens or personal data

### Security (section 5, hard cap if a real secret is committed)
- No passwords, keys, tokens or connection strings in code, tests, fixtures or docs. Read them from environment or `.env` (git-ignored). Add new names to `.env.example` with empty values
- Database access through parameterized queries or the ORM only. Never build SQL from user input. Never pass user input to shell commands, `eval` or `exec`
- Authentication and authorization checked server-side in the API before any protected resource is touched. Passwords are handled by Supabase Auth, never stored by our code
- Enforce the project-specific limits from the Security wiki page server-side (simulation hours x replications cap, timeouts, rate limits)

### Dependencies (section 9)
- Add a package only when merged code uses it. Pin the exact version in `requirements.txt` (runtime) or `requirements-dev.txt` (tools). No two libraries for the same job
- Every new library needs a "Library Comparisons" wiki entry (template above) in the same PR
- Copied third-party code needs a comment with source and licence

## Tests (section 2)

A feature counts as tested only with a meaningful test of its behaviour, and as edge-tested only with a test of an invalid input, boundary, failure or alternative path. Every task adds both.
- Assert specific values or behaviour. Not allowed: tests with no assertion, asserting a constant, only checking `is not None`, duplicate cases, tests that do not run the code they name
- Where components interact (simulator modules together, API with database, front end with API), add an integration test that checks the interaction. Use fixtures or mocks for Supabase, never the live database
- Project-specific tests: determinism (same seed gives identical output), property tests for safety rules (Hypothesis), data-processing tests for GTFS extraction and the walking-time fit, performance checks for sweeps once they exist
- Run before finishing: `ruff check .`, `ruff format --check .`, `pytest`. All must pass

## Finishing a task

End every task with this block for the team to copy:

```

- <path> (new | changed) - <AI level>

- <test name>: <what it protects>

File size and comments:
- <path>: <lines> lines, <comment ratio>% comments

PR size: <n> changed source lines -> <minimum reviewers, or split plan if over 400>

Wiki entries drafted:
- Design Patterns: <pattern and where, or none>
- Library Comparisons: <library, or none>

Suggested commits:
- <Imperative summary naming the component> (#<issue>)
  AI-assisted: Claude, <level>

PR description: (filled-in template, see below)

Follow-ups outside this task's scope:
- <item, or none>
```

### Commit messages (section 7)
- Imperative, says what changed and which component: `Add minimum gap check to train departures (#14)`. Not `fix stuff`, `update`, `wip`
- Reference the issue with `#<n>` (or `Fix #<n>` on the closing commit)
- Course rule: AI use must be acknowledged on every commit, PR and issue. Add a trailer line `AI-assisted: Claude, <level>` to commits that contain AI-generated code
- If another member contributed, mention them with `@username` or a `Co-authored-by:` trailer

### PR description
Fill `.github/pull_request_template.md`: `Closes #<n>`, what changed, how it was tested (name the tests, including the edge case), AI contribution level, AI-assisted files, how the AI-generated code was verified. PRs are merged with a normal merge commit, never squashed.

### PR size and reviewers
Changed lines = added plus changed lines of source code only. Tests, test fixtures, generated files, lock files and static assets (images, data files) are not counted.

| Changed lines | Minimum reviewers |
|---|---|
| 1 to 250 | 1 (2 if possible) |
| 251 to 400 | 2 |
| Over 400 | Split into smaller PRs, unless the extra lines are static files |

Measure from the repo root (Git Bash). `git diff --numstat` counts a changed line as one addition, so the added column is exactly "added plus changed":
```
git diff --numstat origin/main...HEAD -- . ':(exclude)tests/**' ':(exclude)**/*.test.ts' ':(exclude)**/*.test.tsx' ':(exclude)**/fixtures/**' ':(exclude)config/**' ':(exclude)**/*.json' ':(exclude)**/*.lock' ':(exclude)**/*.md' ':(exclude)**/*.png' ':(exclude)**/*.svg' | awk '{s+=$1} END {print s+0, "changed source lines"}'
```
State the count and the required reviewers in the PR description. Plan the work so a task stays under 400 lines; if it will not, propose the split (for example: data layer PR, then logic PR, then UI PR) before writing the code, not after.

### AI_USAGE.md
For each substantive feature with substantial AI help, draft a row for the features table and, for at least half of them, a short development example: task, files, PR, how the code was verified (test or review comment), and any AI mistake that was found and corrected.

## Reviewing a PR

A review only counts if it shows the code was examined. Write at least one specific technical comment, for example:
- "Checked that the minimum gap is applied on arrival and departure; the boundary test at exactly h_min covers it"
- "The scenario validator rejects negative replications but not zero; add a case"

Check in this order: matches the issue and the math page; tests cover main and edge cases; input validation and error handling; no secrets or unsafe SQL; size and complexity limits; comment ratio of new and changed files; PR size and enough reviewers for it; Design Patterns and Library Comparisons wiki entries where needed; AI declaration in files and PR. Never write only "LGTM". If a change is requested, the fix or a technical reason for not fixing must appear before merge.

## Failed attempts

Trying something that does not work is acceptable if it is documented. Keep the attempt on a branch or in a closed PR, and draft a short note for the issue or engineering notebook: what was tried, why it failed, what was chosen instead.

## Feature counting reminder

Only completed user stories that change application behaviour and satisfy at least two of: business rules or validation, multi-step workflow, calculation or algorithmic processing, coordination of components, authorization, background processing, external service integration, domain-specific logic. CRUD, routing, styling, docs, CI and refactors alone do not count. Closely related micro-stories count as one feature.
