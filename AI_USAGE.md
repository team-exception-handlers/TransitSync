# AI Usage

This file records how AI tools were used to build TransitSync. It is kept consistent with the two other places AI use is declared:

- **Source files:** every source and config file starts with a `# AI contribution: <level>` line (or the equivalent comment in that language)
- **Pull requests:** every feature or fix pull request declares the level for the code it introduces or substantially modifies, and lists the files that received substantial AI help (see `.github/pull_request_template.md`)

All three are good-faith estimates. When they disagree, the pull request is corrected before merge and this file is updated in the same pull request.

## Declaration levels

| Level | Meaning |
|---|---|
| No substantial AI-generated code | Written by a team member. AI was used at most for questions, explanations or small suggestions that were rewritten |
| Below 50% AI-generated | AI generated part of the code, but most of it was written by a team member |
| 50% or more AI-generated | AI generated most of the code. A team member reviewed, tested and edited it |

Code generated by AI counts as AI-generated even after a team member edits it. A declared level is never lowered later.

## Development examples

### 1. Departure counts during a hold

- **Task:** fix the counts on `TrainDeparture` (boarded B, alighted A, onboard load L) so they include passengers who board while a train is held
- **Files:** `simulator/engine/events.py`, `simulator/engine/event_queue.py`, `tests/conftest.py`, tests in `tests/simulator/engine/`
- **Pull request:** [#102](https://github.com/team-exception-handlers/TransitSync/pull/102)
- **AI mistake found:** the AI-generated design scheduled the `TrainDeparture` at the hold decision, for a time later in the simulation. Events are immutable, so the counts were fixed before the hold started and anyone boarding during the hold was missing. A team member (@MusmusIRQ) found this in code review
- **Correction:** a held train now schedules a `HoldEnd` event at the end of the hold, and the `TrainDeparture` is created only when `HoldEnd` is handled. The scheduler rejects a `TrainDeparture` that is not at the current time, so the mistake cannot come back. The event schema moved to version 2
- **Verification:** `test_passenger_boarding_during_a_hold_is_counted_on_the_departure` (one passenger boards during the dwell and one during a 40 s hold; the departure shows B = 2 and L = 2), `test_passenger_arriving_exactly_as_the_hold_ends_still_boards` (boundary case), `test_departure_scheduled_ahead_of_time_is_rejected`

### 2. Reusing an output folder

- **Task:** make sure a run's `events.jsonl` and `summary.json` always come from the same run
- **Files:** `simulator/engine/runner.py`, `simulator/engine/event_log.py`, `tests/simulator/engine/test_runner.py`
- **Pull request:** [#102](https://github.com/team-exception-handlers/TransitSync/pull/102)
- **AI mistake found:** the AI-generated runner wrote straight into an existing folder. A failed rerun left the old results behind, and a failed summary write could leave a new event log next to an old summary. A team member (@MusmusIRQ) found this in code review
- **Correction:** the runner rejects a folder that already holds either file before the run starts, and a failed run removes everything it wrote, including partial files
- **Verification:** `test_rerun_into_a_folder_with_previous_output_is_rejected_and_keeps_it`, `test_folder_with_either_output_file_is_rejected_naming_it`, `test_existing_folder_with_unrelated_files_is_accepted`, `test_failed_summary_write_leaves_no_output`

### 3. Event queue tie order

- **Task:** process events by time, then by a fixed priority for events at the same time, then by scheduling order, so every run is reproducible
- **Files:** `simulator/engine/event_queue.py`, `tests/simulator/engine/test_event_queue.py`
- **Pull request:** [#102](https://github.com/team-exception-handlers/TransitSync/pull/102)
- **Verification:** the expected orders in the tests are written out by hand from the documented tie order, not computed with the code under test. Hypothesis property tests (`test_processing_order_never_goes_backwards`, `test_order_does_not_depend_on_scheduling_order_for_distinct_keys`) check that processing order and the clock never go backwards and that the result does not depend on the order events were scheduled in. `test_scheduling_earlier_in_tie_order_at_current_time_is_rejected` covers the edge case of a boarding scheduled at a time that has already been processed further along the tie order

### 4. Optional passenger event recording

- **Task:** #21, record passenger timelines and allow detailed recording to be disabled for sweep runs
- **Files:** `simulator/engine/event_log.py`, `simulator/engine/runner.py`, `tests/simulator/engine/test_event_log.py`, `tests/simulator/engine/test_passenger_recording.py`, `README.md`, `AI_USAGE.md`
- **Pull request:** [#103](https://github.com/team-exception-handlers/TransitSync/pull/103)
- **Design:** reuse the existing versioned event records. Add a keyword-only `skip_event_types` argument to `run_scenario`, as agreed in the review of #102. Only the write to `events.jsonl` is filtered; components and summary counts still receive every event. Copy the filter before components start so it cannot change during a run. Record the sorted skipped types in `summary.json` so downstream analysis can detect an incomplete event log
- **Verification:** two scripted passenger journeys cover alighting, platform arrival, a missed connection and boarding. Tests compare the full and filtered runs' handled events, final boarded passengers and summary counts, and verify that the summary identifies omitted types in stable order. Other cases cover same-time ordering, deterministic filtered output, invalid filters, empty filters and filtering every event type. All tests, Ruff lint and formatting checks passed locally
- **Integration limit:** passenger generation and boarding logic remain separate tasks. The tests use a small scripted component to emit the existing passenger event types

### 5. Corridor throughput cap and queueing

- **Task:** #20, limit corridor throughput, queue excess passengers and calculate each passenger's queueing delay
- **Files:** `simulator/passengers/corridor.py`, `tests/simulator/passengers/test_corridor.py`, `README.md`, `AI_USAGE.md`
- **Pull request:** [#106](https://github.com/team-exception-handlers/TransitSync/pull/106)
- **Design:** represent the bottleneck as a deterministic FIFO queue with passage slots `60 / capacity_per_minute` seconds apart. The first passenger after an idle period passes immediately, and unused capacity is not banked. Return passage and delay timestamps without depending on the unfinished passenger entity or walking-time sampler
- **Verification:** hand-calculated tests cover a simultaneous burst, arrivals joining an existing queue, an arrival exactly on the next slot, idle periods, invalid inputs and fixed walking times feeding the event scheduler. A Hypothesis property checks that consecutive passages never exceed the configured rate. Full suite: 116 passed; Ruff lint and formatting checks passed locally
- **Integration limit:** tasks #17-#19 remain open. Their future passenger movement component must call the queue with each passenger's bottleneck-arrival time and schedule `PassengerArrival` at the returned passage time

### 7. Passenger entity and demand-based generation

- **Task:** #17, create individual passengers with identity, origin, destination and state; generate them from time-varying demand and configurable transfer fractions
- **Files:** `simulator/passengers/passenger.py`, `simulator/passengers/demand.py`, `simulator/passengers/generation.py`, `simulator/passengers/__init__.py`, `simulator/engine/random_streams.py`, and the three matching passenger test files
- **Pull request:** [#134](https://github.com/team-exception-handlers/TransitSync/pull/134)
- **Design:** use immutable passenger snapshots and piecewise-constant demand rates in passengers per minute over simulation-second intervals. Integrate each band's overlap before sampling a Poisson count; this distribution is an explicit modelling choice because the task does not prescribe one. Draw destinations separately, sorting their configured station IDs so mapping order cannot change seeded results. Append the `destinations` stream without moving existing stream indices
- **Verification:** hand-calculated examples include a window crossing demand bands with an expected count of 21. Tests cover invalid input without RNG or ID consumption, zero demand and zero-sized draws, weighted destinations, stable IDs, independent random sources and reproducibility across generated seeds. A Hypothesis property verifies that splitting a demand window preserves expected volume
- **Integration limit:** this task returns passenger batches. Train-triggered pulses and platform arrival timing are #18; boarding, alighting and missed connections are #100. No train component is required for #17

### 8. Pulsed transfer arrivals

- **Task:** #18, generate each transfer group on an actual train arrival, then spread platform arrivals by individual walking times rather than a continuous arrival process
- **Files:** `simulator/passengers/transfer_component.py`, `simulator/passengers/__init__.py`, `simulator/engine/events.py`, the new transfer test file and the updated event schema/queue tests; one existing generation-test import had trailing whitespace removed
- **Pull request:** [#134](https://github.com/team-exception-handlers/TransitSync/pull/134)
- **Design:** accumulate demand between actual arrivals independently for each station/feeder-platform pair. Reuse #17's generator and #19's walking sampler. Add `CorridorArrival` and bump the event schema from 3 to 4 so #20's corridor queue receives walkers in chronological order across overlapping groups. Retain passenger snapshots, stable burst IDs and passage timestamps for #100 and metrics
- **Verification:** fixed walks of 5, 6 and 10 seconds following trains at 100 and 400 seconds produce platform arrivals at 105, 106, 110, 405, 406 and 410, with a quiet gap. At 30 passengers/minute, simultaneous corridor arrivals at 15 seconds pass at 15, 17 and 19, with delays 0, 2 and 4. Tests also cover reversed walk order between groups, separate demand clocks sharing one corridor, configuration validation and same-time departure boundaries. A Hypothesis property checks that delaying a feeder shifts the whole pulse. A real `TrainComponent` run checks delayed arrivals, byte-identical logs and filtering without changing passenger state. Full suite: 241 passed; Ruff checks passed
- **Integration limit:** the component stops at the connecting platform. Boarding, destination-based alighting, missed connections and train load/count coordination remain #100. Demand-driven transfer groups are not capped by the feeder train's aggregate onboard load in this task

### 9. Boarding, alighting and missed connections

- **Task:** #100, move passengers between platforms and trains while doors are open, alight at the destination, board FIFO and record missed connections
- **Files:** `simulator/passengers/boarding_component.py`, `simulator/passengers/transfer_component.py`, `simulator/passengers/__init__.py`, `simulator/trains/train_component.py`, and `tests/simulator/passengers/test_boarding_component.py`
- **Pull request:** [#134](https://github.com/team-exception-handlers/TransitSync/pull/134)
- **Design:** share passenger snapshots and persistent train entities, reserve pending seats/IDs, process destination alighting before boarding, and keep per-stop movement counts in the train component. Treat actual departure as door closure, including minimum-gap waits; exact-time arrivals can board under the established event priority. Log late/full missed connections while retaining the waiting passenger for a subsequent train. The transfer component only changes WALKING snapshots to WAITING, preserving later boarding/completion states
- **Verification:** a full two-seat train alights one passenger and boards one, departing with B=1, A=1 and L=2. Boundary cases include 120 seconds versus 120.001 seconds. Tests cover multiple open trains, compatible destinations, later trains, initial manifests, untracked occupied seats, repeated stops and a 90-second separation wait with a passenger boarding during that wait. Hypothesis verifies FIFO, capacity and passenger conservation. End-to-end tests cover transfer walking, boarding and destination completion, with byte-identical output, optional passenger filtering and both component dispatch orders. Full suite: 267 passed; Ruff checks passed
- **AI correction during verification:** the full-journey test initially supplied only three seats for a larger generated group while expecting everyone to complete. Its fixture now supplies sufficient capacity; separate tests retain explicit capacity/left-behind assertions
- **Integration limits:** feeder transfer groups remain external demand. Their initial alighting records increment the feeder's alighting count without decrementing the existing remaining aggregate load, which never included those newly generated passengers. The component keeps scheduled dwell; door-flow calibration, dynamic dwell and hold strategy decisions are separate
